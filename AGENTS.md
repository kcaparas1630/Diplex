# AGENTS.md

Guidance for coding agents working in this repository.

## Project

Diplex renders and converts documents for consumer apps. A consumer uploads a DOCX or PDF and gets page images to display, a JSON description of the content to navigate, and on-demand export to PDF or DOCX.

- Architecture (source of truth): [docs/architecture.md](docs/architecture.md)
- PDF to DOCX pipeline: [docs/pdf-to-docx.md](docs/pdf-to-docx.md)

When a change alters the design, update those documents in the same change.

## Repository Layout

Planned; not scaffolded yet.

```
Dockerfile                     builds the diplex-core service image (Python, LibreOffice, font library)
diplex-core/                   Python service (uv)
  src/diplex_core/
    definition/                Pydantic models: the API contract (source of the OpenAPI spec)
    engine/
      docx_to_pdf/
      pdf_to_docx/             the workflow in docs/pdf-to-docx.md
      pages/                   PDF -> WebP page images
      extract/                 Docling -> content JSON
      fonts/                   font library and resolution rules (shared by both conversions)
    api/                       FastAPI routes: upload, sign, export, delete
    storage/                   S3 access, tenant-scoped sessions, presigned URLs
  tests/
diplex-sdk/                    @diplex/sdk (TypeScript)
  procedures/                  upload.ts, getDocument.ts, export.ts, index.ts
  client/
    types.gen.ts               generated from diplex-core's OpenAPI; never edited by hand
    http.ts
  index.ts
diplex-store/                  @diplex/store (TypeScript)
  tables/
    documents.ts               Drizzle table + SCHEMA_VERSION
  migrations/                  SQL generated by drizzle-kit, for consumers on any ORM
diplex-playground/             sample website that consumes Diplex through @diplex/sdk (never published)
docs/                          architecture and pipeline documents
samples/                       real test documents (git-ignored, never committed)
```

- The Python folder is named `diplex-core`, but the importable package is `diplex_core`, because Python names cannot contain hyphens.
- `engine/fonts/` is shared by the DOCX to PDF and PDF to DOCX pipelines. "Resolve" refers only to the font-resolution step, not to the engine as a whole.

## Architecture Rules

Do not break these without updating `docs/architecture.md` first.

- **The service is stateless.** No database, no manifest or metadata files in S3. Everything the consumer needs is returned in the response.
- **Only the service talks to S3 with credentials.** The SDK and consumer apps never hold AWS credentials. Browsers download through presigned URLs only.
- **The SDK is the only consumer interface.** Consumer code never reads or writes the Diplex table directly; the SDK does, through the consumer's own database connection.
- **Never store presigned URLs.** Store the opaque `location` and sign on demand. URLs signed with role credentials expire when the role session ends.
- **Every S3 key starts with the tenant ID.** The service resolves the tenant from the API key and accesses S3 through a session limited to that tenant's prefix.
- **S3 holds originals and page images only.** Exports are never stored. The JSON is stored in the consumer's database.
- **`location` is opaque** to the SDK and consumers; only the service knows the S3 layout.
- **The Pydantic models in `diplex-core/src/diplex_core/definition/` are the API contract.** FastAPI generates the OpenAPI spec from them, and `diplex-sdk/client/types.gen.ts` is generated from that spec. Change the Pydantic models, then regenerate; never edit the generated types by hand.
- **Dependencies point one way: `diplex-sdk` imports `diplex-store`, never the reverse.** The store only defines tables; its `content` column is plain JSON, and the SDK returns it typed.
- **The playground is an ordinary consumer.** `diplex-playground` uses only the SDK and its own database, exactly like a customer app. It never imports `diplex-core`, reads the S3 bucket, or holds AWS credentials.
- **The Drizzle table in `diplex-store/tables/` is the canonical database schema.** Any change bumps `SCHEMA_VERSION` and ships a migration generated by drizzle-kit. The SDK refuses to start against an older schema.

## Documents Are Untrusted Input

- Run every LibreOffice job in its own process, with its own profile (`-env:UserInstallation`) and `FONTCONFIG_FILE`, a hard timeout, and no network access. Kill the process when the job ends.
- Work in a per-job scratch directory and wipe it afterwards.
- Reject macro-enabled files, enforce file size and page limits, and guard against zip bombs (DOCX is a zip).
- Never log document contents.

## Dependencies and Licensing

- **No AGPL dependencies** (for example PyMuPDF, pdf2docx). GPL tools only as separate processes.
- Check the licence before adding any dependency, and record it in the relevant doc.
- Fonts in the font library must allow embedding, because exported DOCX files embed them.

## Tooling

- **Python:** 3.11+, managed with `uv`; tests with `pytest`; HTTP API with FastAPI.
- **TypeScript:** package manager and test runner to be decided when `diplex-sdk`, `diplex-store` and `diplex-playground` are scaffolded. The playground's web framework is also undecided. Types are generated from the OpenAPI spec with openapi-typescript; migrations with drizzle-kit.
- **Docker:** the service image builds from the root `Dockerfile`.
- Add the exact build, test, and run commands here once they exist.

## Testing

- Every module gets unit tests. Run the full test suite before reporting work as done.
- Measure conversion quality on real documents in `samples/`, not synthetic ones. Do not generate sample documents.
- When a result is compared against Word, say so; when it is not, do not claim Word fidelity.
- Report results faithfully, including failures and numbers that look bad.

## Working Agreements

- Ground technical recommendations in current documentation, specifications, and vendor docs, and cite sources. Do not rely on recalled knowledge for standards, limits, or prices.
- Ask before destructive actions (deleting files, resetting state, removing images).
- Do not commit unless asked.
- In architecture docs, describe each concept in 3 to 5 bullets.
