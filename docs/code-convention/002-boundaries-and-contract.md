# Convention 002: Boundaries and the API Contract

Do not break these without an ADR that changes [ADR 001](../adr/001-architecture.md).

## Engine

- **The engine is stateless.** No database, no storage, no storage credentials, no knowledge of customers. It renders a request and forgets it.
- **Authentication and limits live in the hosted gateway, never in the engine.** The engine's only authentication is an optional static key for self-hosting.

## SDK and Storage

- **Storage belongs to the consumer.** Only the SDK talks to the bucket, with the consumer's own credentials, on the consumer's server. Credentials never reach the engine or a browser.
- **The SDK runs on the server only.** It must never be bundled into browser code. Browsers receive presigned GET URLs only.
- **Only `createDocument` calls the engine.** Get, update, delete and export work from the consumer's database and bucket alone.
- **The SDK is the only consumer interface.** Consumer code never reads or writes the Diplex table or the document folders directly; `location` is opaque to it.
- **Never store presigned URLs; delete removes the files.** Store the `location` and sign on demand, and `deleteDocument` deletes the bucket folder, not only the row.

## Contract and Packages

- **The Pydantic models in `diplex-core/src/diplex_core/definition/` are the API contract.** FastAPI generates the OpenAPI spec from them, and `diplex-sdk/client/types.gen.ts` is generated from that spec. Change the Pydantic models, then regenerate; never edit the generated types by hand.
- **Dependencies point one way: `diplex-sdk` imports `diplex-store`, never the reverse.**
- **The Drizzle table in `diplex-store/tables/` is the canonical database schema.** Any change bumps `SCHEMA_VERSION` and ships a migration generated by drizzle-kit. The SDK refuses to start against an older schema.
- **The playground is an ordinary consumer.** `diplex-playground` uses only the SDK, its own bucket and its own database. It never imports `diplex-core`.
